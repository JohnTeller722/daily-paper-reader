## 摘要
个性化AI智能体需要用户记忆：一种持久化的用户模型，通过多次对话构建并在每次新对话中参考。当前，这种记忆几乎总是以非结构化文本、知识图谱或扁平的事实存储形式存在，并通过检索方式查阅——即获取与当前请求最相似的条目。这种“事实袋”记忆能够较好地回忆单个事实，但由于存储事实和执行操作是分离的步骤，它在解决矛盾、聚合多条记录或强制规则方面存在困难。我们认为，用户记忆应该可执行。我们提出“用户即代码”（UaC）范式，其中智能体对用户的模型是一个活着的软件项目：类型化的Python对象保存用户状态，普通Python函数编码管理状态的规则，因此表示和推理用户发生在同一个媒介中，解释器可直接运行。实现机制是一个两阶段管道：一个只追加的日志，从不丢弃任何事实，并定期检查点化为类型化代码。这改变了记忆的能力。在标准的长时对话基准测试中，UaC在召回率上匹配了全上下文上限和最强的先前记忆系统（LOCOMO上78.8%）。其优势在表征至关重要的地方显现。在涉及用户历史的聚合性问题（如“我去年进行了多少次国际旅行？”）上，基于检索的记忆崩溃（6-43%），而UaC保持近乎完美（99%），因为答案是对类型化状态的一行计算，而非在文本中搜索。此外，由于其规则在状态变化时确定性执行，UaC能够呈现未经请求的、安全性关键的警报——例如新处方药物与数月前记录的过敏症冲突——这是查询驱动记忆无法提供的功能。

## Abstract
A personalized AI agent needs a user memory: a persistent model of who the user is, built across many conversations and consulted on each new one. Today this memory is almost always stored as unstructured text, a knowledge graph, or a flat store of facts, and consulted by retrieval -- fetching the entries most similar to the current request. Such "bag-of-facts" memory recalls individual facts well, but because storing a fact and acting on it are separate steps, it struggles to resolve contradictions, aggregate over many records, or enforce rules. We argue that user memory should instead be executable. We introduce User as Code (UaC), a paradigm in which an agent's model of a user is a living software project: typed Python objects hold the user's state and ordinary Python functions encode the rules that govern it, so representing and reasoning about the user happen in one medium an interpreter can run. The enabling mechanism is a two-phase pipeline: an append-only log that never discards a fact, periodically checkpointed into typed code.   This changes what memory can do. On standard long-term conversation benchmarks, UaC matches both a full-context upper bound and the strongest prior memory systems on recall (78.8% on LOCOMO). Its advantage emerges where representation matters most. On aggregate questions over a user's history -- "how many international trips did I take last year?" -- retrieval-based memory collapses (6-43%) while UaC stays near-perfect (99%), because the answer is a one-line computation over typed state rather than a search over text. And because its rules execute deterministically whenever the state changes, UaC can surface unsolicited, safety-critical alerts -- such as a newly prescribed drug that conflicts with an allergy recorded months earlier -- a capability query-driven memory cannot provide.

### 2. 论文提出的方法论：核心思想、关键技术细节

-   **核心思想：用户即代码（UaC）**：将用户模型重塑为一个动态演化的软件项目。其核心在于 **“可执行性”**，即用户状态和规则以 Python 代码形式呈现，可以被 Python 解释器直接运行。
-   **关键技术细节**：UaC 通过一个**两阶段管道**将非结构化对话转化为可执行代码：
    1.  **第一阶段：记忆 (Memorize) - 追加式事实提取**：
        -   **过程**：对每次会话，使用 LLM（如 Gemini 3 Flash）提取所有事实，格式化为扁平字符串。这些事实被**追加**到一个只读列表中，**永不覆写或删除**。
        -   **作用**：保证了信息的完整性，避免信息丢失。该阶段本身不进行任何结构化处理，专注于“记忆”。
    2.  **第二阶段：结构化 (Structure) - 定期代码生成**：
        -   **过程**：定期（或按需）运行，LLM 根据累积的完整追加事实列表，**重新生成**整个用户记忆的**类型化 Python 代码**。这包括类型化的 dataclass 对象（如 `PassportInfo`）、集合（如 `trips = [Trip(...)]`）以及用于存储“非结构化”事实的 `notes` 字段。
        -   **关键优势**：代码是**从头重新生成**的，而非增量式修改，避免了增量操作中信息丢失的风险。这确保了代码化表示是对所有已知事实的最佳整合。
-   **约束执行与主动服务 (Active Service)**：
    -   **过程**：在生成代码的同时，一个“编码代理”会编写 Python 函数（称为“约束”），这些函数定义了对用户状态进行安全检查的规则（如“检查即将到期的护照是否与国际旅行日期冲突”）。这些约束在每次状态更新后都会被确定性执行。
    -   **输出**：约束执行的结果（如警报）会被汇总到一个精简的**清单（Manifest）**中，在未来的任何对话开始时自动加载。智能体无需用户提问即可主动提示这些警报。
-   **多层次检索机制**：在回答问题时，UaC 结合多种信息源：
    -   **结构化代码状态**：直接加载相关域（domain）的类型化 Python 代码到提示词中。
    -   **事实向量检索**：对追加事实列表进行检索，作为代码可能遗漏的“长尾”事实的备选。
    -   **原始存档检索**：对原始对话文本进行检索，用于需要精确措辞的查询。

### 7. 优点：方法与实验设计的亮点

-   **方法创新性**：将“用户记忆”的观点从“数据存储”转变为“可执行逻辑”，这是一个新颖且有力的想法，直接解决了检索式记忆的固有问题。
-   **两阶段管道设计**：`追加式日志（Memorize）+ 定期检查点代码（Structure）`的设计分离了“记忆”和“组织”的职责，类似于现代数据库的 WAL 和 Checkpoint 机制，兼顾了信息完整性与计算效率。这是一个优雅的工程化解决方案。
-   **新基准的构建**：论文指出了现有基准的局限性，并构建了**分析推理基准**和**主动服务基准**。这使得 UaC 的核心优势能够被量化衡量，为后续研究提供了有价值的评估工具。
-   **严格的实验控制与公平对比**：通过自行复现 SOTA 方法并进行公平对比，同时进行跨 LLM 和跨 Judge 的鲁棒性验证，极大增强了结论的可信度和说服力。
-   **成本效益分析**：分析了 UaC 的令牌成本及其摊销特性，尤其是在多次查询场景下的成本优势，这对于实际部署至关重要。

### 8. 不足与局限

-   **写入成本**：UaC 需要两轮 LLM 调用（提取+结构化），相比于单次提取的扁平事实系统，写入开销更大。虽然结构化成本在多次读取后被摊销，但对于只查询一两次的用户来说，成本收益为正的门槛较高。
-   **结构化状态对于纯召回的贡献有限**：实验证明类型化代码状态对标准召回任务提升不大，且可能因压缩导致细节丢失。这意味着对于仅需要简单事实回忆的场景，UaC 可能并非最优解。
-   **主动服务依赖管道**：UaC 的主动服务能力高度依赖于其约束生成和执行管道。如果没有这个管道（如 `UaC (no alerts)`），其主动服务检测率会大幅下降至 52.5%。
-   **分析推理基准的局限性**：该基准是合成的，数据“模式整洁”。在真实世界的嘈杂数据中，结构化的优势可能更明显，但也可能因为数据质量问题而引入新的挑战。此外，基准是单次查询设计，这是 UaC 的最坏情况。
-   **复现和基础设施偏差**：论文明确指出其对比 SOTA 方法时使用了简化的基础设施（如 ChromaDB 替代了论文原版复杂的检索栈），并使用了较弱的 LLM 作为 backbone。论文的结果是与这些简化版比较得出的，不能直接等同于与 SOTA 论文原始结果的对比。
-   **跨 LLM 覆盖有限**：跨 LLM 验证仅在 Gemini 和 GPT-5.4 上进行，对于较小的代码生成模型，其生成代码质量可能不高，UaC 的优势可能会减弱。
-   **需要沙盒环境**：将用户记忆存储为可执行代码带来了安全风险，需要严格的沙盒执行环境来防止代码注入或跨用户数据泄露，这增加了部署的复杂性。
-   **硬场景的统计显著性不足**：在 20 个困难主动服务场景上，UaC 与 Mem0 的差距虽直观存在，但在统计上并不显著（p=0.69），因为样本量太小（n≈200 才能达到显著性）。作者对此有诚实的说明。
